# RP-W4 — Public MCP gateway and REST API

Date: 2026-08-13  
Status: approved  
Program: [`2026-08-13-rp-program-design.md`](2026-08-13-rp-program-design.md)  
Depends on: W0 (`lib/channels/` tool registry, `lib/autonomy/`), `auth-service` (RS256 JWT + JWKS)  
Migration range: **160–169**  
Owned paths: `ads-agent/app/api/public/`, `ads-agent/lib/publicapi/`, `ads-agent/mcp/public-gateway/`

## Problem

Ryze's headline developer claim is "API to let AI manage your ads — 150+ tools, one endpoint, OAuth once", usable from Claude, ChatGPT and Cursor. Our MCP servers (`mcp/context-server`, `mcp/google-ads-server`, `mcp/app-data-mcp-server`) are internal: reachable only inside the compose network and authorised by a short-lived internal task token minted for Hermes profiles. There is no external client story, no OAuth, no published catalogue and no rate limiting.

## Goals

1. A single externally reachable MCP endpoint exposing the tool catalogue generated by W0's channel registry plus curated read tools.
2. OAuth 2.1 authorisation conforming to the MCP authorization specification, with per-tenant scopes.
3. A documented REST surface covering the same operations for non-MCP integrators.
4. Every mutating tool routed through `evaluateAutonomy()` — an external caller can never obtain a write path that bypasses the gate.

## Non-goals

- Publishing tools for SEO/GEO/CMS surfaces in this workstream — those register descriptors later through the same registry; W4 ships the gateway, not their catalogues.
- Self-serve signup, billing or plan management (`lib/metering` already meters usage; commercial packaging is out of scope).
- Replacing the internal MCP servers or the Hermes task-token path, which remain unchanged.

## Standards basis

Per the [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization), a protected MCP server acts as an **OAuth 2.1 resource server**. It therefore MUST implement OAuth 2.0 Protected Resource Metadata ([RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728)) for authorization-server discovery, SHOULD support Dynamic Client Registration, and MUST validate token audience binding so a token minted for another resource cannot be replayed against ours. `auth-service` becomes the authorization server; the gateway is the resource server.

## Architecture

```text
Claude / ChatGPT / Cursor / curl
        │  OAuth 2.1 (PKCE), audience-bound access token
        ▼
/.well-known/oauth-protected-resource   (RFC 9728 metadata → auth-service)
        │
        ▼
mcp/public-gateway  ──►  scope check  ──►  tool dispatch
        │                                     ├─ read tool  → context-server / app-data reads
        │                                     └─ write tool → proposal → evaluateAutonomy()
        │                                                          ├─ gate  → returns proposal id, status pending
        │                                                          └─ auto  → executes, returns result
        ▼
rate limiter + metering ledger + audit log
```

The gateway never holds platform credentials or calls a platform API itself; it composes existing servers and the executor.

## Tool catalogue

Descriptors come from `listToolDescriptors()` (W0), so the public catalogue cannot drift from what adapters actually implement. Each descriptor is decorated with a required scope:

| Scope | Grants |
|---|---|
| `ads:read` | Performance, search terms, campaign structure |
| `ads:propose` | Create proposals; never executes |
| `ads:write` | Execute through the autonomy path (gate or auto per policy) |
| `crm:read` | The six curated read tools already exposed by `mcp/app-data-mcp-server` |
| `context:read` | Context graph / spaces reads |

`advance_opportunity_stage` and any other tool the internal app-data server withholds stays withheld — the public gateway may expose a subset of internal tools, never a superset. A registry test asserts this containment.

## Data model (migrations 160–162)

```sql
CREATE TABLE adsagent.api_clients (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id       uuid NOT NULL,
  name         text NOT NULL,
  scopes       text[] NOT NULL,
  rate_limit_per_min integer NOT NULL DEFAULT 60,
  state        text NOT NULL DEFAULT 'active' CHECK (state IN ('active','suspended')),
  created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE adsagent.api_call_log (
  id           bigserial PRIMARY KEY,
  org_id       uuid NOT NULL,
  client_id    uuid NOT NULL,
  tool_name    text NOT NULL,
  mutating     boolean NOT NULL,
  proposal_id  uuid,
  decision     text,
  status_code  integer NOT NULL,
  latency_ms   integer NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now()
);
```

Both carry RLS `FORCE` and a leading-edge `org_id` index (GC6). `api_call_log` is the external-caller audit trail and is joined to `proposals` for any mutation.

## REST surface

The same operations as documented HTTP endpoints under `/api/public/v1/`, sharing the dispatcher with the MCP path so the two cannot diverge:

```
GET  /api/public/v1/performance?channel=&from=&to=
GET  /api/public/v1/campaigns
POST /api/public/v1/proposals                → { proposalId, decision, reasons[] }
POST /api/public/v1/proposals/{id}/execute   → honours autonomy; 409 if gated and unapproved
GET  /api/public/v1/proposals/{id}
GET  /api/public/v1/tools                    → the same catalogue MCP advertises
```

`POST /proposals` accepts an `Idempotency-Key` header (GC5). OpenAPI 3.1 is generated from the same descriptors, so docs cannot drift either.

## Rate limiting and metering

Per-client token bucket at `rate_limit_per_min`, enforced before dispatch, returning `429` with `Retry-After`. Every call writes to the metering ledger via the existing `lib/metering` path so external usage is billable and visible alongside internal agent usage.

## Interfaces

**Consumes:** `listToolDescriptors`, `getAdapter`, `evaluateAutonomy`, `lib/metering/ledger`, `auth-service` JWKS verification (`lib/auth/dal.ts` pattern).

**Produces:**

```ts
export function dispatchTool(ctx: PublicCallContext, name: string, args: unknown): Promise<ToolResult>;
export function requiredScopeFor(toolName: string): string;
export function buildOpenApiDocument(): OpenApiDocument;
export function checkRateLimit(clientId: string): Promise<{ allowed: boolean; retryAfterMs?: number }>;
```

## Error handling

Unauthenticated or audience-mismatched tokens return `401` with a `WWW-Authenticate` header pointing at the protected-resource metadata, per the specification. Missing scope returns `403` naming the required scope. A gated write returns `202` with the proposal id rather than an error — the caller learns the action is pending approval, which is the honest semantics of a supervised system. Adapter errors surface with their W0 class so an integrator can distinguish a retryable failure from a platform rejection.

## Testing

- `scopes.test.ts` — every mutating descriptor requires `ads:write`; no descriptor is exposed without a scope.
- `containment.test.ts` — the public catalogue is a strict subset of internal tools; a deliberately added internal-only tool does not leak.
- `autonomy-path.test.ts` — a write tool call with `ads:write` still produces a proposal and honours `gate`; there is no code path from `dispatchTool` to `adapter.execute` that skips `evaluateAutonomy`.
- `ratelimit.test.ts` — bucket refills, `429` carries `Retry-After`.
- `openapi.test.ts` — generated document validates against OpenAPI 3.1 and lists exactly the catalogue's operations.
- `w4-gate.test.ts` — full external call path with a signed token: metadata discovery, audience validation, scope check, dispatch, metering entry, audit row.
